# EasyBlue 0.2.2 통신 경로 재검토

2026-10-20. 원본 EXE 및 DLL의 정적 분석과 기존 실행 기록을 대조했다. 새 앱의 Windows/동글 실기 검증을 완료했다는 의미는 아니다.

## DLL과 새 입력 엔진

KMHook.dll의 init(10001BC0), installHook(10001CA0), uninstallHook(10001E00), setMode(10001F70), 저수준 키보드 콜백10001990 및 마우스 콜백10001A10을 재대조했다. 원본은 프로세스 간 공유 상태와 전역 훅을 사용한다. 새 WPF 앱은 이 x86 DLL을 로드하지 않고 자체 저수준 훅과 직렬 USB 작업자를 사용한다. 따라서 이 버전은 원본 DLL의 바이너리 패치가 아니다. 기존 EBTiny와 동시 제어를 막는 처리, PC 복귀, 키 해제, 훅 해제 경로를 유지했다.

## 이름 및 이번 범위 밖의 기능

원본의 DeviceName 접근 함수4035F0/403740은 SYSTEM/DeviceName 로컬 설정을 읽고 쓴다. 이것을 원격 폰 이름 조회 프로토콜로 해석하지 않았다. 새 앱의 표시 이름 저장과 Windows Bluetooth 캐시 가져오기는 별도 기능이다. 검토한 제어 vtable의 나머지 EB02/EB04 경로는 펌웨어/저장 영역 관련 기능이며, 페어링 복구를 위해 추측해서 사용하지 않는다. B001 및 기존 키맵·클립보드·펌웨어 관리 전체를 재구현했다고 주장하지 않는다.

## 검증과 남은 확인

세션이 비활성 상태이면 제어 명령을 거부하는 가짜 전송기를 사용해 초기 연결부터 페어링까지 검사했다. 초기화 순서, 버전 불일치 시 제어 금지, 초기화 실패 시 페어링 금지, 초기화 중복 방지, 종료와 재접속, 취소 시 재초기화, 실제 펄스 거부 시 반복 금지, 준비 상태 조회 횟수 제한을 포함한다. 전체 핵심 검사는123개다.

사용자 로그는23C0의 명시적 거부를 확인한다. 세션 초기화 누락은 원본 대비 확정된 구현 차이이고 이 현상을 설명할 수 있지만, 사용자의 실제 동글에서 이것이 유일한 원인이었는지는 새 실행으로 확인해야 한다. Linux에서는 WPF, 전역 훅, 트레이 및 물리 USB/Bluetooth를 실행 검증하지 못했다. 새 로그의 인터페이스 버전, 초기화 완료, 상태 flags와 실제 실패 단계로 남은 원인을 구분할 수 있다.
